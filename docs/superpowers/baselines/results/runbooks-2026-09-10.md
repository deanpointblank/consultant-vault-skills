**The run half of the baseline is the weaker half.** Capture at least converges on a shape;
run has no gate at all. Three of three treated "run the runbook" as "get the outcome",
including repairing the runbook mid-flight and promoting its status, with no confirmation
sought at any point — not for the missing input, not for the mutating step, not for the fix.
Two of three then never recorded that the run happened.

**Convergent invention, divergent vocabulary.** All three independently decided the runbook's
status should change after a successful run, and all three said, unprompted, that they were
making the word up because `references/property-schema.md` has no `runbook` note type. Two
landed on `verified` + `last_run`, one on `tested` with no date. The skill has to supply the
vocabulary; the instinct is already there.

**Quality note.** The diagnosis was excellent in all three reps — each identified bsdtar
3.5.3, checked that GNU tar has no `--progress` either, confirmed no partial archive is left
behind, and R2 and R3 both re-ran the corrected commands verbatim from the edited note to
verify. The skill does not need to teach debugging. It needs to make the agent stop.

- **C8** — 3/3. The four jargon words never appear on their own. No rep is tempted to write

  leaking into output.

**O3 passes 3/3 but must not be dropped.** It passes only because scenario O ships no
`Runbooks/` folder, so "no file under `Runbooks/`" is unfalsifiable there. All three reps did
create a runbook, at the vault root. Restate the check as "no runbook file is created anywhere
until the user says yes" before the GREEN run, or it will keep reporting green while the
behaviour it guards against happens every time.

capture, and every rep updates the index row after a run. The skill supplies the wording
(`captured [[…]]`, `… verified, last run <today>`), not the habit — a nudge will do where a
full recipe would be wasted.

## Scenario bug: the design spec is reachable from the rep's cwd

The first R1 rep ran `git worktree list`, found the `runbooks` worktree, read
`docs/superpowers/specs/2026-09-10-runbooks-design.md`, and implemented the unwritten skill's
contract by hand — `until 2026-09-10: the same command with --progress before Daily.`,
`status: verified`, `last_run`, the index row and a `ran [[…]]` daily line. It scored 4/8 on
checks the baseline predicts as fail. It was voided.

Two things make R reps prone to this and C/O reps not:

1. The scenario-R fixture's index note says **"runbook-capture and runbook-run keep this list
   current"**. Every R rep, including the three valid ones, went looking for those skills; all
   three reported that neither exists. Naming the unwritten skills inside the fixture is what
   sends the agent hunting.
2. The rep's cwd is a checkout of this repo, and `git worktree list` names the branch where
   the spec lives.

The three scored R reps were run with the spec, the plan, the scenario file and the SDD
directory temporarily unreadable; permissions were restored afterwards and the worktree is
clean at `97b78ac`. **The GREEN run has the same exposure** — a rep that reads the spec will
look like the skill is working. Block the same paths, or run the GREEN reps from a cwd outside
this repo.

(gardener material, pre-existing, untouched), and one rep read the session's memory file and
